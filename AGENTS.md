# AGENTS.md — входная точка для ИИ-агентов

**Перед любыми изменениями в этом репозитории обязательно прочитайте
`docs/RULES.md` — обязательные строгие правила работы с проектом.
Начинать работу без их прочтения запрещено.**

Краткая выжимка (полные формулировки — в `docs/RULES.md`):

1. **Типология «туфты» — 6 форм**: метрическая подгонка (Закон Гудхарта),
   семантическая подмена (Goal Drift), круговая порука (тавтология),
   имитационная сложность (Cargo Cult), сломанный превью/окружение, самосертификация.
   Любая форма — нарушение дисциплины, обязательное к объявлению в отчёте.
2. **Ролевой дуализм**: каждый работает и как ПРОДЮСЕР (делает), и как
   ЧЕЛЛЕНДЖЕР (спрашивает). Обязательный вопрос на каждом этапе:
   «Мог ли этот этап пройти успешно, пока исходная задача останется нерешённой?»
3. **Запрет самосертификации**: любой отчёт/статус обязан нести маркер
   `АУДИТОР: ВНЕШНИЙ` (названия верификатора/инструмента + дата) или
   `АУДИТОР: САМ` (проверка в рамках того же конвейера). Формулировки
   «100% проверено/верифицировано» без маркера автоматически читаются как:
   «Информация предоставлена самими респондентами, не подтверждена
   независимыми источниками.»
4. **Граница автономности**: внутри согласованной цели — максимальная
   автономия без вопросов («запустить ли тест?», «пересобрать ли?»).
   Любые новые сущности, требования, гипотезы или оценки вне исходной цели —
   самовольное расширение скоупа, нарушение дисциплины.
5. **Итоговый отчёт — строго 12 разделов** (цикл `docs/RULES.md`, п. 5),
   ОКОНЧАТЕЛЬНЫЙ СТАТУС — только один из: ЗАВЕРШЁННЫЙ / ЧАСТИЧНО ЗАВЕРШЕНО /
   ЗАБЛОКИРОВАНО / ОТКЛОНЁННЫЙ / ГИПОТЕЗА.

6. **Toyota Quality Gate** (`docs/RULES.md`, §6): MAIN → аудит → дефект →
   классификация → Root Cause → Issue → исправление → тесты → независимый
   Challenger → Main Re-Audit → стандартизация. Merge/зелёный CI — не DONE;
   production-функции подтверждаются production-контуром.
7. **P0/P1 = Stop the Line**: остановить затронутый контур, немедленно оформить
   GitHub Issue с симптомом, воздействием и воспроизведением; при невозможности
   исправить сразу — containment, владелец и остаточный риск. Возобновление —
   по условиям §6.2, не по одному факту merge.
8. **Существенные дефекты** (критерии в §6.2): обязательны Root Cause / 5 Why,
   Poka-Yoke (канонический домен, DRY/DDD/SOLID, regression/E2E, серверные
   безопасность/ownership), независимый Challenger и Kaizen.
   Шаблон: `.github/ISSUE_TEMPLATE/significant-defect.yml`.
   Самопроверка не заменяет независимый аудит; после merge проверить актуальный
   SHA `main`. Непроведённые проверки указывать явно, не объявляя завершение.

Дополнительные договорённости репозитория:

- `docs/SCHEMA-REQUESTS.md` — очередь заявок SR-XXX на изменения схемы данных;
  инфраструктуру данных напрямую не редактировать.
- `docs/INFRA.md` — runbook Supabase/Resend/Pages.
- Смоук-проверки: `verify_pages.py`, `verify_app.mjs`, `verify_auth.mjs`,
  `verify_profile.mjs`, `verify_telegram.mjs`; локальный запуск —
  `python3 devserver.py 8765`.
- Правило целостности превью (форма 5 «туфты»): если задача затрагивает UI,
  «готово» только после прогона `verify_pages.py` против реального
  `devserver.py`, а не только после юнит-проверок в JS.
