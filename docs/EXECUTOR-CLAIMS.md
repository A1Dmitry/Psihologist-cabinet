# Исполнители и claim-протокол (кто над какой задачей работает)

Нормативное правило — [RULES.md §6.17](RULES.md#617-идентичность-исполнителя-и-claim-протокол-wip-1).
Этот документ объясняет, как правило применяется и что именно оно гарантирует.

## 1. Зачем

В проекте параллельно работают несколько исполнителей (агентские сессии, человек).
До протокола не было видно: кто взял Issue, кто уже работает, чьи это коммиты. Отсюда
два наблюдаемых дефекта процесса:

- два исполнителя берут один и тот же Issue и дублируют работу;
- «три P0 одновременно»: никто не «держит» задачу, приоритет размывается.

Claim-протокол вводит **идентичность исполнителя** и **фиксацию владения Issue**
без новой инфраструктуры: только git-ветка, файл карточки и комментарий в Issue.

## 2. Идентификатор: EXEC-XXXXXXXXXX

```text
ID = base64url(SHA-256(seed)).slice(0, 10)     10 символов [A-Za-z0-9_-]
Отображение: EXEC-XXXXXXXXXX
```

Seed выбирается автоматически (`node tools/claim.mjs id`), в порядке приоритета:

| Приоритет | Источник | Когда |
|---|---|---|
| 1 | `--seed` / `EXECUTOR_SEED` | ручной запуск, тесты |
| 2 | файл `.executor-seed` (gitignored) | человек/агент хочет постоянную личность |
| 3 | имя ветки `arena/<session>-…` | агентская сессия: у каждой ветки свой стабильный ID |
| 4 | `user@host` | последний рубеж локально |

Пример: seed `branch:arena/01a0d7f9-psihologist-cabinet` → `EXEC-9OFSmjqDq_`.

**Честные границы:** seed не секрет и не удостоверяет личность — им можно
притвориться. Протокол решает задачу координации, а не безопасности; настоящая
авторизация — там, где ей место (GitHub permissions, RLS). Не помещайте в seed
PII, токены и пароли: он может попасть в отчёты.

## 3. Взятие Issue

```bash
node tools/claim.mjs take 67            # взять
node tools/claim.mjs status             # кто что держит (из любой ветки)
node tools/claim.mjs release 67         # закончил — освободить
node tools/claim.mjs mine               # мои задачи и мои коммиты
```

`take` делает три вещи, и все три нужны:

1. читает удалённые маркеры Issue и решает, свободно ли (`acquire`), продление
   (`refresh`), конфликт (`conflict`, exit 2) или перехват истёкшего
   (`takeover-stale`, только с `--force --reason "…"`);
2. публикует **CLAIM-комментарий** в Issue — это единственный кросс-веточный
   источник истины, его видно из любой ветки и клона;
3. коммитит **карточку** `.claims/issue-<N>.<EXEC>.json` в текущую ветку.

Второй исполнитель на активный Issue получает:

```text
Issue #67 держит EXEC-9OFSmjqDq_ (ветка arena/01a0d7f9-…), до 2026-09-25T12:41:00Z.
Возьмите другое Issue или дождитесь release/истечения TTL.        exit 2
```

TTL по умолчанию 90 минут (`--ttl`), продление — повторный `take` владельцем.
Истёкший claim (`STALE`) не «освобождается молча»: перехват требует явного
`--force` и причины, а карточка сохраняет `handover_from`.

## 4. Состояния и честность

| Состояние | Значение |
|---|---|
| `FREE` | активных маркеров нет — Issue можно брать |
| `CLAIMED` | держит исполнитель, TTL не истёк |
| `STALE` | держал исполнитель, TTL истёк — нужен release или явный перехват |
| `UNKNOWN` | GitHub недоступен/нет прав — **состояние неизвестно** |

`UNKNOWN ≠ FREE` (RULES §6.15): CLI никогда не печатает «свободно», если не
прочитал удалённые маркеры. Без канала `take` отказывает (exit 3) и не создаёт
карточку; осознанный обход — `--offline-ok`, и тогда отсутствие публичного
маркера становится явным блокером в отчёте.

`status` также краснеет (exit 2), если **два исполнителя** одновременно держат
один Issue, и если в ветке лежат две активные карточки на один Issue.

## 5. Видимость своих изменений

- Владелец Issue виден в `status` и в CLAIM-комментарии;
- коммиты исполнителя помечаются трейлером `Executor: EXEC-XXXXXXXXXX`
  (`node tools/claim.mjs commit -m "…"` добавляет его автоматически);
- карточки `.claims/*.json` в ветке — видимая история «кто брал и когда отпустил»,
  рядом с изменениями, с которыми она связана.

```bash
git log --grep="Executor: EXEC-9OFSmjqDq_" --oneline    # мои коммиты
gh pr list --search "EXEC-9OFSmjqDq_"                    # PR с моим ID
```

## 6. Коды выхода и права на публикацию

| Код | Значение | Что делать |
|---|---|---|
| `0` | успех (claim/release/status/commit) | работать |
| `1` | ошибка использования (нет номера Issue, нет `-m` для commit) | исправить команду |
| `2` | **конфликт владения** (или двойной захват в `status`) | взять другое Issue / дождаться release |
| `3` | **состояние неизвестно**: GitHub недоступен, маркеры не прочитаны | восстановить канал; обход — только `--offline-ok` |
| `4` | **маркер не опубликован**: права/ошибка публикации | выдать `issues:write` либо осознанный `--offline-ok` с блокером |

Публикация CLAIM-комментария требует **права писать комментарии в Issues**.
Интеграция с частичными правами (например, может создавать Issue, но не
комментировать — HTTP 403 `Resource not accessible by integration`) публичный
маркер поставить не сможет. Реальное наблюдение и поведение инструмента:

```text
$ node tools/claim.mjs take 69
· карточка: .claims/issue-69.EXEC-9OFSmjqDq_.json (active, до …)
· CLAIM НЕ опубликован: Message: Resource not accessible by integration
БЛОКЕР: карточка записана, но CLAIM-маркер в Issue #69 не опубликован.
Другие исполнители не увидят владение и могут взять тот же Issue.
exit 4
```

То есть claim без публичного маркера — **блокер, а не тихий успех**; `status`
дополнительно показывает такие карточки как `unpublished` (риск дубля).
Владелец либо выдаёт исполнителю право комментировать Issues, либо работа
ведётся с «искусственной остановкой» и фиксацией блокера в отчёте.

## 7. Что протокол НЕ делает

- не заменяет права GitHub: `take` не «бронирует» Issue на сервере;
- не мешает человеку взять Issue без claim — но тогда это нарушение §6.17,
  и его видно в `status`;
- не гарантирует завершение работы: исполнитель может пропасть, поэтому TTL есть,
  а перехват истёкшего claim — штатный сценарий;
- не читает всю историю комментариев: `status` смотрит окно 24 часа и помечает
  вывод `PARTIAL`, если окно могло быть обрезано.

## 8. Проверка (Poka-Yoke)

`tests/executor-claims.mjs` входит в общий гейт (`npm run verify`): идентификатор,
маркеры, карточки, конфликты, CLI целиком (подменный `gh` + изолированный
`--root`) и негативные контроли — «двойной захват Issue краснеет», «нет GitHub →
UNKNOWN, а не FREE».

Демонстрация fail-before-fix (2026-09-25, ветка `arena/01a0d7f9-…`):

| Намеренная поломка | Результат прогона |
|---|---|
| конфликт владельцев игнорируется | `4 FAILED`, exit 1 — второй исполнитель реально получил карточку |
| трейлером считается любое упоминание ID | `1 FAILED`, exit 1 — трейлер `Executor:` не добавлялся |

Файлы после демонстрации восстановлены, прогон — `ALL PASS (43)`.
