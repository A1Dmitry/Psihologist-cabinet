## 1. ПЕРВОНАЧАЛЬНАЯ ЦЕЛЬ

«Ещё» со всеми остальными — все 15 разделов со смартфона), safe-area, бейдж
«Ожидание», десктопный сайдбар без деградации; строки главной/расписания/журнала →
карточки с primary-действием и меню «…» (цели ≥44px, деструктивные отделены и
подтверждаются через UI-диалог); тексты и структура десктопа не меняются.
Границы: схема БД/RPC/Edge не трогаются; «готово» — после `verify_pages.py`
против живого `devserver.py` + зелёного `npm run verify`.

## 6. ТУФТА НАЙДЕНА

1. `[x]` в теле #63 при отсутствии таб-бара в коде — «готово» на бумаге.
   Не принято на веру: ground truth снят grep'ом по `origin/main`
   (таб-бара нет) до взятия задачи.
2. Замер `npm run verify | tail` показал exit 0 при 8 красных наборах —
   код выхода пайпа, а не гейта. Перезамер без пайпа + переустановка
   `embedded-postgres` дали честные 40/40, exit 0.
3. Три silent-артефакта fuzzy-правок при статусе «success»: 2 мусорных
   фрагмента в `js/app.js` (сломанный `renderBooking`, хвост `gin' } };`),
   2 неприменённые правки (строка расписания, класс бейджа сайдбара).
   Пойманы перепроверкой каждой правки (`node --check`, grep, тесты) —
   ни один артефакт не ушёл дальше рабочей ветки.
4. Собственный стаб-тест неверно моделировал `dataset` (`data-cab-menu` →
   `dataCabMenu` вместо `cabMenu`) — пойман падением поведенческой проверки,
   исправлен; реальное поведение контроллера было корректным.

## 7. КОРЕННЫЕ ПРИЧИНЫ

- (п.6.3) Статус «success» инструмента правок не гарантирует ни применения,
  ни точечности: fuzzy-совпадение может сработать мимо цели и дописать
  фрагменты в конец файла. Системная причина — отсутствие обязательной
  сверки результата правки с ground truth до следующего шага.
- (п.6.1) Причина `[x]` в #63 неизвестна (история правок тела issue
  недоступна) — фиксируется как UNKNOWN, а не как факт.
