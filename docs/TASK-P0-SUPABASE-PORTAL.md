## 2. Что именно является задачей (интерпретация без добавления требований)

Три обязательных результата, все — серверно обеспеченные (RLS/Edge Function/RPC),
а не клиентскими фильтрами:

1. **Email-redirect возвращается в опубликованное приложение**, а не на
   `localhost` (`project_context.current_email_redirect_problem`).
2. **Одноразовая привязка** аккаунта Supabase Auth к существующей записи
   психолога: код хранится хешем, гасится атомарно, привязка — только после
   подтверждения email и только по identity из проверенной сессии.
3. **Изоляция данных**: психолог видит ровно свой профиль и свои записи/запросы;
   второй психолог, `anon` и непривязанный `authenticated` — ноль строк.

`acceptance_tests` раздела 1 = Definition of Done. Дополнительно действуют гейты
`docs/RULES.md` §6 (включая §6.10 privacy/security и §6.11–6.12 E2E/negative
checks) и §6.13–6.16 (observability, каноническая бизнес-логика, fresh state,
shared boundaries).

## 4. Параметры, без которых задачу нельзя безопасно завершить

Спецификация прямо запрещает угадывать (`output_rules[1]`, `[3]`). До получения
значений реализация не стартует:

1. **`app_url`** — production-домен приложения. Кандидат из `docs/INFRA.md`:
   `https://a1dmitry.github.io/Psihologist-cabinet/`. Подтвердить или заменить
   (кастомный домен?).
2. **`auth_callback_path`** — точный путь/hash callback-обработчика для фактического
   фреймворка (SPA на hash-роутинге: отдельный `/auth/callback` физически
   невозможен на Pages без редиректа; нужен фактический маршрут, например
   `#/auth/callback`, либо подтверждение введения страницы-обработчика).
3. **Auth-flow**: остаётся ли код-из-письма (`auth-code`) как канал подтверждения,
   или включается Supabase `signUp` + confirmation link (см. расхождение в разделе 3).
4. **Фактическая схема живой БД**: наличие `psychologists.owner_id`, уникальное
   ограничение на него, фактический набор политик и grants, наличие views
   (`security_invoker`), индексы на полях связей. Проверять на проде, не по
   `schema.sql` (в проде `schema.sql` НЕ подтверждено применённым целиком —
   `docs/CURRENT-STATE.md`, `docs/INFRA.md` п.2).
5. **Таблица кодов привязки**: использовать/расширить существующую
   `auth_login_codes` или ввести отдельную (заявка SR в `docs/SCHEMA-REQUESTS.md`).
6. **Что такое «запросы»** в терминах этой схемы (кандидаты: `sessions`,
   `waiting_items`, `booking_attempts`, `client_entries`) — точный перечень
   связанных таблиц для RLS.
7. Доступы владельца для Dashboard-шагов и production-проверок (песочница агента
   не имеет сети до `supabase.co`).

Секреты (service role key, JWT secret, `RESEND_API_KEY`, пароли) в чат и в
репозиторий не передаются — только Dashboard/`supabase secrets`
(`output_rules[2]`, `AGENTS.md`, `docs/RULES.md` §6.13).

- Не удалять таблицы, столбцы, политики и данные; необратимых операций не
  выполнять; перед миграциями показать изменения и их последствия
  (`implementation_steps[4]`, `output_rules[3]`).
- Изменения схемы данных — через заявку SR в `docs/SCHEMA-REQUESTS.md`
  (договорённость репозитория, `AGENTS.md`), а не прямой правкой инфраструктуры.
- Разделять в отчёте: что сделано миграциями/кодом, что включается вручную в
  Supabase Dashboard (`implementation_steps[7]`, `output_rules[4]`).
- Итоговый отчёт — строго 12 разделов (`docs/RULES.md` §5) с маркером
  `АУДИТОР: ВНЕШНИЙ` или `АУДИТОР: САМ` (§3). Любой P0/P1 дефект по ходу —
  Stop the Line (§6.2, §7 `AGENTS.md`).
- Если задача затрагивает UI: «готово» только после `verify_pages.py` против
  живого `devserver.py` (`AGENTS.md`, форма 5 «туфты»), плюс `npm run verify`.
