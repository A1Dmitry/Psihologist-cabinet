## 1. Что сделано по задачам

### T-01 · Многошаговый wizard записи ✅

Шаги **«Услуга → Время → Контакт»** (`index.html` → `#page-booking`, состояние —
`BookingViewModel`).

- Индикатор прогресса (`#book-steps`): три шага с состояниями «готово / текущий /
  недоступен»; по пройденным шагам можно вернуться кликом, вперёд — только когда шаг
  заполнен.
- Кнопки **«Назад» / «Далее»** (`#book-back`, `#book-next`) + «Записаться»
  (`#book-submit`, только на шаге 3). «Далее» недоступна, пока не выбран слот,
  и подписано, чего именно не хватает (`#book-nav-hint`).
- **Данные не теряются**: состояние выбора живёт в VM (`serviceId`, `date`, `time`,
  `step`), поля ввода — в статическом DOM (перерисовка меняет только контейнеры
  списков), поэтому «назад/вперёд» сохраняют и выбор, и введённый текст.
- Переходы между шагами сопровождаются плавным скроллом к началу формы.
- В шаге 3 есть **recap выбора** с кнопками «изменить» (услуга / время).
- Валидация на каждом шаге: без услуги не пустит на шаг 2, без времени — на шаг 3;
  если выбранный слот заняли, пока форма открыта (async free/busy), клиента
  возвращает на шаг 2 с понятным сообщением.
- **Старые ссылки работают**: `?book={slug}` и `/psy/{slug}#book` по-прежнему
  ведут на страницу записи (роутинг не менялся), `/book/{slug}` — как раньше.

### T-02 · Слоты по длительности услуги ✅

`BookingViewModel._slotsFor(date)` (публичный `get slots()`):

- слот недоступен, если **`start + duration_min > конец приёма`** — конец окна
  считается как `max(последний слот + шаг сетки, slot_end)`;
- слот недоступен при **пересечении** с чужой записью или блокировкой
  (интервалы в минутах: `start < занято.to && занято.from < start + длительность`);
- слот недоступен, если **время уже прошло** (для «сегодня»).
- Занятые часы зачёркнуты, причина — в `title` («не хватает 90 мин до конца
  приёма», «время уже прошло», «Время занято» / заголовок блокировки).
- Счётчики свободных окон на табах периода и отметка «нет окон» на чипах дней
  считаются по тем же правилам.
- **Длительность чужой записи** берётся из её услуги; для серверного free/busy
  (`public_booked_slots`) длительность пока неизвестна → берётся шаг сетки
  (ограничение закрывается заявкой **SR-003**).

Проверено автотестом на услуге 90 мин (приём 10:00–19:00, шаг 60 мин):
`18:00` закрыт (18:00 + 90 мин = 19:30 > 19:00), `17:00` доступен,
`16:00` закрыт при занятом 17:00, `15:00` свободен, для 60-мин услуги `18:00`
доступен.

### T-03 · Часовой пояс клиента ✅

- Утилиты поясов вынесены в `js/services/calendarService.js` (моя зона):
  `detectTimeZone`, `zoneOffsetMinutes`, `formatUtcOffset`, `zonedTimeToUtc`,
  `formatInZone`, `dateInZone`, `convertWallClock`, `isPastMoment`. Считаем через
  `Intl` и абсолютные моменты — корректно на DST и при смещениях вида ±5:30.
- Пояс клиента: `Intl.DateTimeFormat().resolvedOptions().timeZone` (определяется
  один раз), пояс специалиста: `session_settings.timezone` (уже есть в
  `public_settings`, fallback `Europe/Minsk`).
- Подпись под сеткой (`#book-tz-note`):
  «Время специалиста: Europe/Minsk (UTC+3). Ваш пояс — Asia/Tashkent (UTC+5),
  разница +2 ч. Например, 12:00 у специалиста — это 14:00 по вашему времени.»
- В ячейке слота при чужом поясе: крупно — время специалиста, мелко —
  «19:00 у вас» (со сдвигом суток, если слот «уехал» на другой день).
- В recap и в тексте заявки — то же двойное время.
- **В БД пишется время специалиста** (сетка расписания — его), пояс клиента
  фиксируется в заметке заявки: «Часовой пояс клиента: Asia/Tashkent (UTC+5) —
  время записи в поясе специалиста: Europe/Minsk.» Колонку не добавлял —
  подал **SR-001** (`sessions.client_timezone` / `client_utc_offset`).

### T-04 · «Услуга → сразу окна» ✅

- На странице записи клик по услуге = услуга выбрана **и сразу открыт шаг 2 со
  свободными окнами этой услуги** (время сбрасывается, т.к. сетка зависит от
  длительности).
- Со страницы специалиста каждая услуга — ссылка
  `/book/{slug}?service=<id>` → запись открывается сразу на шаге «Время» с
  выбранной услугой и её окнами. Ссылка обычная (не SPA-хендлер), поэтому
  работает и как реальный переход/для сканера; после загрузки каталога страница
  перерисовывается корректно.

## 4. SEO (моя зона: `js/services/seoService.js`)

- `applyNoIndex()` — честный `noindex,nofollow` для несуществующих
  `/psy/{slug}` и `/book/{slug}` (CI теперь отдаёт эти маршруты со статусом 200,
  поэтому пустые карточки без этой метки индексировались бы). Ставится **только
  когда каталог точно загружен** (`portalVm.source === 'server' | 'demo'`), чтобы
  валидная страница не успела получить noindex на первой отрисовке.
- `setRobots()` — robots сбрасывается в `index,follow` на каждом `setMeta`, то
  есть noindex не «прилипает» при переходах без перезагрузки.
- Профиль: в JSON-LD добавлены **BreadcrumbList** и **ReserveAction** на
  `/book/{slug}` (карточка отвечает на запрос «запись онлайн»), у организации
  появился `@id`/`url`.
- Запись: заголовок/описание формируются **под выбранную услугу** (длительность и
  цена) + хлебные крошки; canonical — собственный URL.
- Полностью переписан не мой файл не трогался: `sitemap.xml`/`robots.txt`
  генерирует CI (зона Агента 1) — рекомендация по `/book/{slug}` в sitemap
  передана отдельным пунктом в `SCHEMA-REQUESTS.md`.

## 7. Известные ограничения и что предложено дальше

1. **Гонка бронирования (SR-002).** Клиентская сетка честная, серверная проверка
   — пока по точному совпадению времени. Два клиента, нажавшие одновременно,
   могут занять пересекающиеся слоты. Настоятельно рекомендую взять SR-002 в
   работу до реального трафика.
2. **Длительность чужой записи (SR-003).** При шаге сетки 30 мин и чужой
   90-минутной записи клиент покажет лишние пересекающиеся слоты.
3. **Пояс клиента (SR-001)** пока в `note` — это видно специалисту, но не
   структурировано.
4. **sitemap** не содержит `/book/{slug}` (рекомендация Агенту 1).
5. Профиль/запись при **первой** отрисовке до загрузки каталога показывают
   «не найдено» ~0,5–1 с (теперь перерисовываются автоматически; можно добавить
   состояние «Загружаем…» — зона Агента 1/5 на их усмотрение).
