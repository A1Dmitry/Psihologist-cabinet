# #27 — клиентский путь: требования и приёмка

**АУДИТОР: САМ — EXEC-QAE_s4u4vI. Дата: 2026-09-26.**
База анализа: `c6c2f2e7aba7e886d5c0efd6ed40594ddbaaca4b`.
Источник: [issue #27](https://github.com/A1Dmitry/Psihologist-cabinet/issues/27).
Это результат **BA-задачи**, не отчёт о реализации перечисленных функций.
Ни один будущий acceptance-сценарий ниже не помечен как пройденный продуктом.

## 1. ПЕРВОНАЧАЛЬНАЯ ЦЕЛЬ

Зафиксировать будущие требования от лица клиента по всему пути:

**Выбор специалиста → выбор услуги → доступное время → запись → подтверждение →
подготовка → встреча → продолжение / перенос / отмена.**

Покрыть C1–C7 без медицинской диагностики и автоматических терапевтических решений.
Цель клиента: получить ответ из продукта, не обращаться к психологу за информацией,
которая уже есть в системе. Обращение за индивидуальной договорённостью допустимо;
оно не заменяет отображение статуса, цены, правил или результата своего действия.

Владелец назначил #27 этой сессии и разрешил работу несмотря на прежние
организационные блокировки. Локальный claim взят с `--offline-ok`;
GitHub не разрешил публикацию комментария. Это не публичная бронь.
#63 принадлежит другому исполнителю и в эту работу не входит.

### Обязательное уточнение владельца

> «локальное хранилище нужно исключительно для персональных данных, которые
> не видимы другим и не должны быть видимы. общие данные через сервер».

Уточнение применяется ко всем C1–C7. Прежние локальные fallback-режимы —
не образец целевого решения. В этом документе «общие» означает **данные
совместного процесса с доступом по полномочиям**, а не «доступные всем».

## 2. РЕЗУЛЬТАТ — целевой продуктовый контракт

### 2.1. Акторы, данные и источник истины

| Класс | Примеры и назначение | Где хранить и кто видит |
|---|---|---|
| Личные, не предназначенные другим | Приватные персональные заметки, не опубликованные клиенту и не включённые в совместный процесс | Только локальный защищённый сейф их владельца; не отправлять на сервер, в логи, аналитику, уведомления или резервный облачный blob автоматически |
| Общедоступные | Опубликованный профиль, услуги, цены каталога, доступные окна без данных клиентов | Сервер; клиент получает только публичную проекцию |
| Совместные операционные | Запись и её цена, статусы, перенос/отмена, согласованные условия, Meet/payment links, запрос регулярного времени | Сервер — источник истины; только соответствующие клиент и психолог, плюс строго необходимые служебные процессы |
| Явно переданные клиенту материалы | Назначенные инструкции, задания, документы | Сервер с адресным доступом; не вся внутренняя карта психолога |
| Намеренно переданные контакты / согласие | Контакт для записи и доставки, факт согласия и версия текста | Минимально необходимый серверный объём, только разрешённым получателям; не копия локального сейфа |
| Состояние доставки / оплаты | События отправки, подтверждение провайдера, серверный финансовый результат | Сервер; клиент видит свою безопасную проекцию, не технические журналы |

**S1.** Общие бизнес-данные не сохраняются в `localStorage`, `sessionStorage`,
IndexedDB, Cache API или офлайн-очереди. Кэш в памяти открытой страницы допустим
только для отображения серверного ответа; после reload — загрузка с сервера.
Private API-ответы не должны попадать в постоянный browser/service-worker cache.
Кэш статических файлов приложения не является хранилищем бизнес-данных.

**S2.** Нет ветки «сервер недоступен → записали локально → success». Без server-ack
запись/запрос/подтверждение не объявляются сохранёнными. Введённые общие данные
можно удерживать в памяти текущей формы до ухода со страницы, без фоновой записи
на диск. При потере ответа показывать «результат уточняется», а не утверждать,
что операция точно не выполнена; повтор — после серверной сверки, идемпотентно.

**S3.** Персональность не равна локальности: отправленный клиентом контакт уже
предназначен выбранному получателю. Личные заметки и передаваемые сообщения —
разные поля/действия. Нельзя синхронизировать весь локальный объект ради одного
поля. Копирование приватного содержимого в совместный материал — только отдельное
явное действие автора с предпросмотром получателя и содержимого.

**S4.** Сам факт хранения локально не обеспечивает невидимость другим.
Использовать существующий `cryptoService`/сейф, не новую криптосхему;
не сохранять рядом открытый текст и ключ. При блокировке/выходе убрать
расшифрованное содержимое из UI/памяти. Очистка хранилища устройства может
необратимо удалить локальные данные: предупреждение обязательно, скрытой
серверной копии нет. Конкретный безопасный экспорт — отдельное решение владельца,
не неявный облачный backup.

**S5.** Права на общие данные проверяет сервер при каждом чтении/действии,
а не URL, clientId из формы или наличие объекта в браузере. Второй клиент,
чужой психолог и аноним без полномочий не получают данные. Клиент не получает
внутренние заметки, риски, чужие контакты и клиническую карту.

**S6.** Общие условия цены, оплаты, времени и ссылки встречи не должны зависеть
от unlock личного сейфа психолога: клиент должен получить их на другом устройстве
из серверной проекции. Приватная заметка к договорённости остаётся отдельно локально.

**S7.** Сессионные секреты авторизации — отдельная техническая граница #40/#41,
не повод хранить под их видом общие данные. Этот BA-документ не объявляет текущую
персистентность токенов допустимым исключением и не меняет её реализацию.
При проектировании хранения нужен отдельный security-review способа сессии;
секретные ссылки не сохраняются в бизнес-снапшоте, аналитике или логах URL.

### 2.2. Карта экранов и ожиданий

| Шаг | Что нужно увидеть | Следующее действие | Если продолжить нельзя |
|---|---|---|---|
| Каталог / профиль | Подходит ли специалист, формат, язык, цена/длительность, ближайшие окна | Выбрать услугу / поделиться публичной ссылкой | «Свободных окон пока нет» отдельно от «Не удалось загрузить» |
| Выбор времени | Дата и время в своём поясе, время психолога, актуальная доступность | Выбрать окно | Обновить окна; не подменять ошибку пустым расписанием |
| Проверка перед контактом | Итоговая стоимость/валюта, длительность, правила оплаты, отмены и переноса | Продолжить к контакту | Условия не определены — не предлагать фиктивное согласие |
| Контакт и согласие | Минимальные поля, получатель, условия обработки, отдельная опция опроса | Отправить запись | Ошибка у поля; не терять уже введённое в открытой форме |
| Результат | Фактический статус записи, следующий шаг, статус оплаты отдельно | Открыть свою запись / добавить в календарь | Неопределённый результат → сверка, не новая заявка вслепую |
| Своя запись | Ближайшая встреча, инструкции, доступные действия, сообщения о результате запросов | Подтвердить / перенести / отменить / восстановить доступ | Истёкшая ссылка → восстановление, без показа содержимого |
| После встречи | Назначенные материалы и следующий согласованный шаг | Повторно записаться / запросить регулярное время | Нет назначения → нейтральное пустое состояние, без автотерапии |

Это текстовый прототип последовательности, **не новые маршруты приложения**.
Существующие `/psy/{slug}`, `/book/{slug}`, `/booking-done`, `/reply` — точки
интеграции. Не создавать параллельную модель записи для клиентского портала.

### 2.3. C1 — понятный выбор специалиста

Каждый ID соответствует одному checkbox исходной issue. Последний столбец —
будущая приёмка в формате «условия → действие → наблюдаемый результат».

| ID | Требование | Acceptance |
|---|---|---|
| C1-01 | Профиль отвечает: кто, с чем работает, формат, цена, длительность, языки/каналы, ближайшее окно | При заполненных данных открыть профиль: все поля доступны до записи. Несколько услуг — цены и длительности привязаны к услугам; «от» только из действующих цен. Неуказанный язык/формат не выдумывается |
| C1-02 | Доступность «сегодня / завтра / ещё» потребляет канон availability | При занятом и свободном слотах показать только допустимые варианты в подписанном поясе. В HTTP/DOM нет имени, причины визита или идентификатора чужой записи. Ошибка загрузки не выглядит как отсутствие окон |
| C1-03 | Явные CTA «Записаться» и «Поделиться» | Скопированная ссылка открывает тот же публичный профиль/услугу в чистом браузере; не содержит токен клиентского портала или приватные параметры. Отмена системного share не выдаётся за успешную отправку |
| C1-04 | Мобильный сценарий основной | На ширинах 320/375/390 px, с клавиатурой и увеличением текста пройти профиль → время → контакт без горизонтальной прокрутки и перекрытых CTA; цели основных действий ≥44×44 px; доступна клавиатурная навигация |

### 2.4. C2 — прозрачная запись

| ID | Требование | Acceptance |
|---|---|---|
| C2-01 | До подтверждения виден полный итог | Для каждой политики оплаты итог показывает услугу, длительность, дату/время/пояс, общую сумму и валюту, сумму сейчас, остаток и срок резерва. Значения после server-ack совпадают с серверной записью; изменившаяся цена требует повторной проверки клиентом |
| C2-02 | Различать время клиента и психолога | Для Europe/Zurich ↔ Europe/Minsk проверить разные даты и переход DST: обе даты/времени подписаны зонами, обозначение «у вас» соответствует выбранной зоне. Несуществующее/неоднозначное локальное время обрабатывается каноном, не угадывается UI |
| C2-03 | Обязательные условия не появляются после контакта | Без ввода имени/контакта открыть правила оплаты/переноса/отмены. Перед отправкой доступен тот же текст и версия. Изменение обязательных условий не принимается молча; согласие не предустановлено |
| C2-04 | Понятные серверные ошибки без ложного успеха | При конфликте слота предложить актуальные окна, при 429 — объяснить ожидание, при outage — честную недоступность. При timeout после commit сверить результат идемпотентной операции. Нет stack/SQL/токена в сообщении; повторный тап не создаёт вторую запись |

### 2.5. C3 — управление записью

| ID | Требование | Acceptance |
|---|---|---|
| C3-01 | Клиент подтверждает свою запись | По действующей ссылке подтвердить запись с телефона, затем открыть с другого устройства: ответ клиента сохранён сервером один раз. Он не превращает неоплаченную запись в оплаченную и не обходит необходимость решения психолога |
| C3-02 | Клиент переносит запись в разрешённых пределах | При допустимом переносе выбрать окно канона и подтвердить последствия. Новый интервал фиксируется атомарно; при конфликте/отказе исходная запись сохраняется. Простой запрос другого времени не меняет запись до принятия |
| C3-03 | Клиент отменяет запись согласно правилам | До действия видеть последствия; после server-ack на другом устройстве запись отменена, слот освобождён по канону, будущие напоминания отменены. Повторный запрос не запускает второй возврат. За дедлайном прямой API тоже отклоняет действие или оформляет разрешённый запрос |
| C3-04 | Клиент восстанавливает ссылку | Ввод контакта возвращает нейтральный ответ независимо от наличия клиента. Новую ссылку получает только доказанный получатель через настроенный канал; rate limit и защита перебора. Старый отозванный секрет больше не работает, другой клиент не получает доступ |
| C3-05 | Гостевой токенизированный доступ без регистрации | Открыть действующую ссылку в чистом браузере без аккаунта: только разрешённые данные/действия адресата. Истёкший/отозванный/изменённый токен не даёт данных. Требование Google относится только к добровольному прикреплению опроса (#41), не к обычной записи |

### 2.6. C4 — подготовка к сессии

| ID | Требование | Acceptance |
|---|---|---|
| C4-01 | Клиент получает подтверждение с фактическим статусом | Сервер создал запись → клиент видит «заявка принята» либо «подтверждено» согласно реальному статусу. Доставка внешнего сообщения проверяется отдельно; отказ доставки не стирает запись и не утверждается как «доставлено» |
| C4-02 | Напоминание приходит без открытого кабинета | Закрыть браузер психолога и дождаться серверного задания на тестовых часах: провайдер принимает сообщение, состояние доставки зафиксировано. Повтор задания не дублирует сообщение; после отмены старая задача не отправляет напоминание |
| C4-03 | Ссылка встречи доступна, когда создана | Для online-записи существующая разрешённая ссылка открывается у клиента; пока ссылки нет — «Ссылка появится здесь», не выдуманный URL. Внешнее сообщение не раскрывает клинический текст; доступ к самой ссылке ограничен участниками |
| C4-04 | До встречи доступны инструкции специалиста | Опубликованную именно этому клиенту инструкцию открыть на другом устройстве. Для offline-встречи доступны адрес/маршрут, для online — инструкции подключения. Внутренние комментарии не попадают в эту проекцию |
| C4-05 | Разделить ознакомление и согласие | Обычная инструкция не требует лишнего согласия. Обработка данных, добровольная передача опроса и юридический документ — разные тексты/цели/версии. Отказ от необязательного опроса не блокирует гостевую запись; отметка «прочитано» не считается подписью |

### 2.7. C5 — клиентский портал

| ID | Требование | Acceptance |
|---|---|---|
| C5-01 | Видны ближайшие встречи | Открыть портал из чистого браузера: сервер вернул только встречи владельца ссылки, сортировка по моменту встречи, дата/пояс и статус однозначны. Пустой список отличается от загрузки/ошибки |
| C5-02 | Перенос и запрос времени различимы | «Перенести» вызывает разрешённую серверную операцию; «Запросить другое время» создаёт pending-запрос после server-ack. Он виден психологу и клиенту на разных устройствах; до принятия исходное время не меняется |
| C5-03 | Meet/payment links соответствуют записи | Показать только разрешённые для этой записи ссылки. Переход/возврат с оплаты не меняет paid: нужен серверный финансовый результат. Устаревшая ссылка/изменённая сумма не используется без проверки |
| C5-04 | Материалы и задания адресные | Один клиент видит назначенный материал, другой не получает его ни через UI, ни прямым запросом/URL файла. Отозванный материал недоступен. Нет автоматического копирования приватного сейфа на сервер |
| C5-05 | История только клиентски релевантная | Показать собственные встречи, результаты запросов, платежную проекцию и назначенные материалы; серверный ответ не содержит внутренние заметки, risk flags, других клиентов. Отменённая встреча остаётся в понятной истории, а не исчезает без объяснения |
| C5-06 | Отзыв — только после разрешённого продуктового решения | По умолчанию в данном скоупе отзыв/рейтинг не включается. До включения владелец утверждает аудиторию, согласие на публикацию, модерацию и отзыв согласия. Нельзя публично раскрывать факт терапии или создавать рейтинг из закрытой обратной связи |

### 2.8. C6 — после встречи

| ID | Требование | Acceptance |
|---|---|---|
| C6-01 | Напоминание о согласованном следующем шаге | Если специалист назначил шаг/следующую встречу, клиент видит его и получает разрешённое напоминание через серверный pipeline. Если назначения нет — система не придумывает рекомендации или следующую дату |
| C6-02 | Назначенные материалы доступны после встречи | Перезагрузить страницу и открыть её на другом устройстве: материалы доступны по серверным правам, не зависят от браузера психолога. Приватный неопубликованный текст не появляется |
| C6-03 | Можно запросить регулярное время | Отправить предпочтение дня/времени/пояса/периодичности: после ack оно видно психологу как запрос, не гарантированная серия. Повтор не дублирует; принятие использует канон availability/series и сообщает фактический результат |
| C6-04 | Понятная повторная запись | Из истории перейти к выбранному специалисту/услуге: заново загрузить доступность и действующие условия. Не переносить старую цену/согласие автоматически, не копировать старую встречу как новую бронь |

### 2.9. C7 — отмена и no-show

| ID | Требование | Acceptance |
|---|---|---|
| C7-01 | Правила видны до оплаты/подтверждения | До контакта и в подтверждении доступны дедлайны и денежные последствия, их зона и версия. Цена, штраф или политика отмены не изменяются задним числом для принятой записи |
| C7-02 | Отмена психологом и клиентом различаются | Сервер фиксирует актора/основание и применённое правило; отмена психологом не увеличивает клиентский no-show. Предложение переноса психологом требует ответа клиента, не выглядит уже согласованным |
| C7-03 | Понятны статус и финансовые последствия | Для каждого разрешённого перехода клиент видит, отменена ли встреча, сколько удерживается/возвращается и состояние возврата. «Возврат запрошен» не означает «деньги возвращены». Фактический возврат подтверждается финансовым серверным событием |
| C7-04 | Запись и платёж — разные состояния | В сценариях «отменено, возврат ожидается», «подтверждено, оплата ожидается», «no-show, оплата получена» оба состояния сохраняются независимо и читаются одинаково из портала/кабинета. Сервер запрещает подмену payment_status клиентом |

### 2.10. Жизненный цикл и политика — один канон

Это **семантическая модель для UX**, не предложение новых SQL-enum:
существующие статусы согласуются с [ROADMAP-OKNA](ROADMAP-OKNA.md), D1/D5 и #31.
Legacy-статус `paid` в записи сам по себе не подтверждает платёж.

| Событие | Что может измениться | Что не следует из него автоматически |
|---|---|---|
| Сервер принял заявку | Создана pending/held-запись по правилам | Встреча подтверждена, оплата получена, сообщение доставлено |
| Клиент ответил «приду» | Серверный ответ клиента | Оплата, одобрение психолога, право занять уже занятый слот |
| Разрешённый перенос выполнен | Время одной записи, версия, связанные календарные/notification artifacts | Финансовое списание без отдельного основания |
| Предложение времени | Pending-запрос | Перенос выполнен, новая серия создана |
| Отмена / истечение резерва | Статус записи и доступность | Возврат денег завершён |
| Финансовое подтверждение | Платёжное состояние по серверному событию | Возрождение отменённой записи или повторное занятие слота |
| Завершение встречи / no-show | Статус встречи уполномоченным актором | Автоматические терапевтические выводы, произвольный штраф |

D5 получает `policy + booking state + server time + actor` и возвращает
допустимое действие/последствия. Deadline сравнивается на сервере; UI только
объясняет решение. На границе дедлайна тестировать `t−1`, `t`, `t+1` согласно
утверждённой политике, не выбирать включённость границы самостоятельно.

Отсутствие настроенной политики не означает «всё бесплатно» или «всё запрещено»:
система сообщает, что требуется согласование, и не выполняет необратимую операцию.
История принятой политики сохраняется отдельно от редактируемых будущих условий.

### Обязательные сквозные приёмки будущей реализации

1. **Два устройства:** A — психолог, B — чистый браузер клиента; затем A закрыт.
   Клиент записывается/читает/запрашивает перенос, результат виден обеим сторонам
   после reload. Для серверных операций локальные business keys отсутствуют.
2. **Запрет локального fallback:** отключить сеть на каждом mutation/read;
   проверять серверное конечное состояние и текст UI. При неизвестном результате
   ни новый объект локально, ни слепая повторная запись не допускаются.
3. **Граница хранения:** локальный приватный маркер не появляется в HTTP payload,
   БД, логах и экспорте общих данных; общий тестовый маркер не записывается в
   постоянные браузерные хранилища. Проверить также service-worker и API cache.
4. **Полномочия:** другой клиент/психолог, anon, подмена session/material/client ID,
   неверный/истёкший/отозванный токен, массовое перечисление, прямой RPC/file URL.
   Ни один отрицательный запрос не меняет данные или не выдаёт приватный ответ.
5. **Гонки:** два клиента на один слот; повтор отправки; перенос против отмены;
   истечение hold против оплаты. Один серверный итог без двойных side effects.
6. **Доставка:** accepted ≠ delivered; повторы, timeout, отмена до отправки,
   закрытый браузер психолога. Проверять сырой server/provider event без PII.
7. **Календарь:** `.ics` при создании/переносе/отмене соответствует серверной
   встрече, не содержит личные заметки. Скачивание файла не означает импорт.
8. **Мобильность/доступность:** размеры из C1-04, focus/errors/клавиатура,
   экранный читатель, загрузка и плохая сеть; результат не только в скриншоте.

Для каждого прогона сохранять дату, SHA, контур, входные тестовые данные,
ожидаемый и фактический результат, идентификатор проверяющего. Не использовать
реальные клинические данные как фикстуры.

## 6. ТУФТА НАЙДЕНА — контрпримеры ложного завершения

- «Сохранилось» в браузере психолога, но чистый браузер клиента ничего не видит.
- «Запрос отправлен» до результата RPC; toast зелёный, у адресата запроса нет.
- «Напоминание доставлено» после изменения локального `sent`.
- «Приватно» потому что текст спрятан в UI, хотя он есть в HTTP-ответе/снапшоте.
- «Сервер — источник истины», но вся общая модель продолжает персиститься локально.
- «Все требования выполнены», потому что написан этот документ или прошёл старый гейт.

Ответ на вопрос RULES §6.3 «Мог ли этап пройти, а задача остаться нерешённой?»:
**да**. BA может быть полным при незавершённом продукте. Поэтому приёмка документа
и реализация перечисленных acceptance-сценариев разделены; чекбоксы issue не
переключаются автоматически.

## 7. КОРЕННЫЕ ПРИЧИНЫ

Причинная цепочка по коду, без придуманного «пятого почему»:

1. Общее действие может выглядеть успешным до получения серверного результата.
2. `addRequest` сперва пишет локальный список, запускает RPC без await и возвращает ok.
3. Портал был построен с local-preview fallback при отсутствии SR-103…107;
   это явно записано в комментарии сервиса и заявках.
4. Общий `dbContext` персистит коллекции без классификации «личное / совместное».
5. Старые локальные проверки не доказывают кросс-девайсный результат и новый S1.

Не установлено этим анализом: фактическое состояние живой БД, масштаб
использования локальных данных пользователями, наличие их единственной копии.
До миграции это нужно проверить, а не предполагать отсутствие данных.

### Миграция хранения: обязательные ограничения

- До изменения `dbContext` выявить потребителей: portal/booking/cabinet,
  clientCabinet/reminder, auth, vault, sync, snapshot-тесты. Общая правка затрагивает
  не только #27; не выполнять её незаметно внутри бизнес-анализа.
- Разделить смешанные legacy-объекты на уровне **полей**, не удалить всю коллекцию
  `clients`/`notes` по названию. Не отправлять старый локальный сейф на сервер.
- Сверить общие записи с сервером. Не импортировать старые демонстрационные
  брони, платежи и локальные success как реальные события. Несверенные локальные
  сведения не выдавать за подтверждённые; при отсутствии авторитетной версии
  миграцию остановить без удаления единственной копии личных данных.
- После безопасного перехода удалить устаревшие общие business keys;
  повторный запуск миграции идемпотентен. Reload не восстанавливает старый снапшот.
- Порядок: серверный контракт → адаптеры → потребители → безопасная миграция →
  новые негативные/двухустройственные тесты. Обновление старых тестов не должно
  просто убирать ассерты: вместо «всё пережило local reload» — раздельные
  инварианты server reload и локального приватного сейфа.
- Rollback приложения не должен восстановить прежний local fallback или
  стереть сейф. При отказе нового контура — честная временная недоступность
  совместных действий, не фиктивная офлайн-работа.

### Kaizen / Poka-Yoke

Критерий защиты от повтора: намеренно вернуть локальную запись общего объекта
или success-before-ack — новый тест хранения/двух устройств обязан упасть.
Намеренно отправить локальный приватный маркер на сервер — privacy-тест обязан
упасть. Эти тесты предлагаются для J1/J2; здесь они **не реализованы**.

Новых принятых записей RRSI нет: независимый Challenger не проводился.
Сигнал «локальный успех ≠ серверный результат» уже описан BA-mobile BL-01…03;
новое требование владельца не выдаётся за самостоятельно доказанный урок.

| Повторная запись | Клиенты с последующей созданной записью / клиенты с завершённой первой встречей в согласованной когорте |
| Использование портала | Уникальные разрешённые portal-open / клиенты с выданным доступом в том же окне; без сырых секретных токенов |

Окна, сроки хранения и целевые пороги утверждает владелец. Payload аналитики
не содержит контакт, содержание заметок/опроса, полные URL, токены или ссылку
на встречу. Удаление дублей — по техническому идентификатору события, а не PII.

**Допустимое повторение и ещё не проверенное:** JS availability и SQL
`create_booking` — намеренные реализации на разных trust boundaries: клиент
помогает выбрать, сервер запрещает недопустимое. Удалять серверную проверку
ради буквального DRY нельзя; правила связывает parity-матрица. Сбор busy/counts
в `BookingViewModel` и `suggestSlots` остаётся в разных адаптерах; полный разбор
семантического расхождения этих входов здесь не выполнен. Следовательно,
утверждение «DRY полностью проверен» было бы недоказанным.

**Изменение плана:** пакеты J1–J5 — доработка этих существующих границ, не
разработка перечисленных возможностей с нуля. Часть старого кода намеренно
не подходит новому требованию владельца; DRY не означает сохранять неверную
локальную семантику только потому, что она уже написана.
