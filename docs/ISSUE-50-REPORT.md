## 7. КОРЕННЫЕ ПРИЧИНЫ

**Почему документы снова разошлись с `main` (повторение после #19):**

1. Документы устарели при каждом merge до новой ручной синхронизации —
   симптом.
2. Синхронизация `CURRENT-STATE.md` не была обязательным артефактом цикла
   merge → Main Re-Audit (Kaizen-кандидат #19 §8 подготовлен 2026-09-24,
   но **отложен без решения**).
3. Отложенный Kaizen не защищает от повторения: дрейф произошёл трижды
   (#19 → PR #52 частичный ресинк → дрейф до `a8953d1` → #50). Системная
   причина — отсутствие Poka-Yoke-шага «ресинк current-state» в STANDARDIZE.

**Почему `verify_cabinet` красный/зелёный по дням (issue #92, кратко):**
тест берёт `vm.series[vm.series.length - 1]`, а `list()` сортирует по
`(weekday, time)`; новая серия (`weekdayOf(today+9)`, `09:00`) оказывается
последней только при weekday > 4 («удачные» Ср/Чт/Пт). Контроль не ловит
перестановки — дата-зависимая фикстура.

  подтверждением служит сопровождающий):
  - Ситуация: любой набор гейта, чей результат зависит от системной даты/порядка
    списка (скользящие `today±N`, «последний элемент = новый»).
  - Антипаттерн: зелёный прогон старого дня сертифицирует гейт; тест проходит
    только в «удачные» дни (второй дата-флейк после `security-regression`/
    `notice-граница` PR #81).
  - Правильное решение: пинить `today` фикстуры; идентифицировать сущности по id
    из результата операции, а не по позиции в сортированном списке; для
    дата-чувствительных наборов — прогон минимум в два разных дня недели либо
    инъекция даты. Доказательство: issue #92, `docs/ISSUE-50-REPORT.md` §3/§7,
    SHA `a8953d1`, 2026-09-26, АУДИТОР: САМ.
