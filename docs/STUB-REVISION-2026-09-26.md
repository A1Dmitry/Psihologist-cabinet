## 1. ПЕРВОНАЧАЛЬНАЯ ЦЕЛЬ

По поручению владельца: ревизия всех заглушек и одна задача на замену реальным
кодом по DDD/DRY/SOLID. Обязательный инвариант владельца:
**локальное хранилище — исключительно закрытые персональные данные;
общие данные совместного процесса — через сервер с разграничением доступа.**

Нельзя заменить требование на «сервер авторитетен, но всё зеркалируется на диск».
Нельзя выгрузить личный сейф на сервер ради синхронизации общего поля.
Кратковременная UI-модель в памяти допустима; постоянный browser cache общих
данных, офлайн-очередь и успех вместо server-ack — нет.

### Что НЕ является заглушкой и не нужно переписывать с нуля

- `availability.js` + серверная проверка `create_booking`: реальные реализации,
  parity-тесты есть. Клиентский UX и серверный enforcement — разные trust boundaries,
  убрать серверную проверку «ради DRY» нельзя.
- `duration.js`, `timezoneService`, `sessionMapper`, `psyMapper`: действующие каноны.
  Default при отсутствующем необязательном поле — не автоматически заглушка.
- `.ics` generator и календарный export уже реализованы (#65). Остаток — lifecycle,
  а не создание второго генератора. Импорт имеет отдельно указанное ограничение R15.
- `uiDialogs` clipboard fallback, lazy-load карты и loading/empty состояния —
  нормальные UI-механизмы; не заменять их «реальным кодом» повторно.
- Google OAuth/GIS и Supabase Auth — реальные вызовы. Настройка provider/deploy
  (#40/#41) не заменяется ещё одной авторизацией; старый auth-code исторический,
  не восстанавливать OTP. Deployment статусы неизвестны в этой ревизии.
- `cabinetStatsService` считает данные, а не рисует фиктивные цифры. Ему нужны
  авторитетные входы; локальное чтение модели в памяти само по себе не stub.
- `cryptoService`/private vault — полезный локальный контур, не удалять.
- `_harness_stubs.mjs`, `tests/*`, `tools/dbtest`, fake-clock и фальшивые fetch
  в тестах — тестовые doubles. Их не подменять production credential/network.
- `seed.sql` и seed каталога — явные фикстуры/начальные данные. Не считать их
  результатом реального бронирования и не допускать скрытый fallback в production.

### Дополнительная граница хранения

`supabaseApi` и Google services хранят session/PKCE/profile; fraud service —
fingerprint. Это не заглушки бизнес-функций, но отдельные технические данные,
которые нужно инвентаризировать при новом строгом storage contract.
Не объявлять их неявным исключением и не удалять вслепую, ломая вход.
Согласовать минимальный безопасный session lifecycle с #40/#41/#29.

`cabinetApi` отправляет поля задач/блокнота/журнала на сервер: необходимо
пофильно классифицировать личный текст и намеренно переданный совместный материал.
Название таблицы не доказывает допустимость серверной публикации. В этой ревизии
не утверждается, что факт текущего server storage означает публичную доступность.

## 3. ПРОВЕРКА

Выполнено `node docs/evidence/stub-audit-probes.mjs` на Node текущей песочницы:
7/7 **воспроизведений дефектов**, не 7 PASS продуктовой приёмки:

1. RPC клиента отклонён → метод уже вернул ok и локальный запрос существует.
2. Нет сессии → кабинетный push не отправил запрос и не вернул ошибку вызывающему.
3. Документ создан/«подписан» произвольной строкой локально без сервера.
4. Прочтение материала отмечено произвольной строкой локально без сервера.
5. Загрузка серии без сессии → ok/localOnly.
6. Запрос согласия на перенос → sent без transport/server вызова.
7. Общие sessions/reminders попали в browser snapshot.

Скрипт использует синтетические данные, in-memory localStorage и запрет сети
до импорта приложения. Это подтверждает поведение JS, **не обход RLS на live**.
После исправления пробы должны перестать воспроизводить дефекты; их нельзя
включать в зелёный quality gate как ассерты желательного поведения.

Полный npm-гейт в этом цикле не запускался: runtime не менялся, его прошлый
зелёный результат не сертифицирует новые требования. Проверки links/syntax/diff
используются только для артефактов ревизии. UI не менялся, новая UI-приёмка не заявлена.

## 4. ПОЛОЖИТЕЛЬНЫЕ РЕЗУЛЬТАТЫ

Получена карта 17 групп с кодовыми точками и конкретным остатком, а не grep-list.
Различены существующий домен, работающие адаптеры, демо, прототип и отсутствие
интеграции. Выявлена прямая DRY-копия storage helpers в `sessionSeriesService`

не просто заменить одну обёртку другой и сохранить нарушение инварианта.

## 5. ОТРИЦАТЕЛЬНЫЕ РЕЗУЛЬТАТЫ

Не проверены runtime на телефоне, deployed functions/schema, delivery receipts,
финансовый provider и доступность портала на независимом устройстве.
Статические находки R10/R11/R15 требуют отдельных negative/integration-тестов.
Наличие таблицы/функции в репозитории не доказывает её деплой.
Наличие локального токена не доказывает утечку чужих серверных данных.

## 6. ТУФТА НАЙДЕНА

Формы ложного успеха: console.warn вместо отказа команды, «отправлено» до
отправки, local document signature вместо проверенного серверного согласия,
серии/запросы, работоспособные только в браузере автора. Само наличие UI и
тестов модели не завершает operational path. Старое утверждение «таблицы
напоминаний нет» неверно для этой базы: `session_reminders` уже существует.

## 7. КОРЕННЫЕ ПРИЧИНЫ / 5 WHY

- Почему клиент видит успех без результата у другого участника? UI/use case
  возвращает успех после изменения локальной модели.
- Почему серверный отказ не влияет? `cabinetApi.push` не возвращает Promise
  результата, другие сервисы запускают RPC без await и поглощают отказ.
- Почему local-only допустим? Прототипы до SR-101…109 встроены как fallback
  в рабочие сценарии; комментарии прямо описывают это решение.
- Почему разрастается несогласованность? Один объект совмещает домен, storage,
  сетевые вызовы и UI-status, а persistent snapshot не разделяет классы данных.
- Почему контроль пропускает? Тесты local-модели/DOM не проверяют независимое
  устройство, fail-after-write/denied RPC и приватную границу хранения.

Это подтверждённая кодом причинная цепочка; исторические мотивы разработчиков
не установлены. Не все 17 групп имеют одну причину: R15 — ограниченный parser,
R11 — trust boundary, provider setup — операционный dependency.

## 8. РЕМОНТ — DDD / DRY / SOLID предметно

### Bounded contexts и агрегаты

- **Booking/Scheduling:** session/series, availability и D5. Инварианты слота,
  переходов, actor и policy — серверные транзакции; UI — проекция результата.
- **Client access/content:** токенизированный доступ, запрос, материал, документ.
  Только минимальный срез адресата, ownership у сервера; без копирования сейфа.
- **Payments:** финансовое событие/платёж и его история отдельно от booking status.
- **Notifications/Calendar:** side effects подтверждённых серверных событий,
  retries/idempotency/delivery states; не собственная альтернативная запись.
- **Private vault:** персональные закрытые данные локально в существующей
  криптографической модели, без фонового server upload.

Не создавать микросервисы/DI-framework/event bus ради терминов. Достаточно
существующих модулей с ясными границами и необходимыми серверными командами.

### DRY — что переиспользовать

`availability`, `duration`, `timezoneService`, `sessionMapper`, существующие
`supabaseApi/cabinetApi`, `calendarService`, `uiDialogs`, `cryptoService`.
Доработать SR-101…109 и уже имеющуюся `session_reminders`; не дублировать таблицы,
портал, payment state, scheduler и календарный generator.
У серверного близнеца availability должен сохраняться parity-контракт.

### SOLID — контракты, а не декорация

- **SRP:** ViewModel не отвечает одновременно за storage, server mutation и
  доставку. Use case оркестрирует результат, домен проверяет инварианты,
  adapter делает I/O, view отображает состояние.
- **OCP:** provider-адаптер заменяется за узким контрактом без изменения правил
  денег/записи; не добавлять неподтверждённых поставщиков ради расширяемости.
- **LSP:** тестовый adapter сохраняет ошибки, idempotency и async-семантику
  реального. Local-only adapter не может подменить server repository в рабочем UI.
- **ISP:** команды записи/отмены/оплаты и чтение проекции имеют необходимые
  контракты, не универсальный «сохранить произвольный объект» без ограничений.
- **DIP:** домен не импортирует DOM/localStorage/fetch; orchestration зависит от
  малых портов. Существующий Supabase adapter — реализация, не повод переписать SDK.

Контракт команды различает confirmed / rejected / outcome-unknown. Timeout
после commit не равен «не создано»: сверка по idempotency key, без двойного
платежа/записи. Server-ack критического действия предшествует success/side effect.

### Порядок и миграция

1. Зафиксировать классификацию полей и реестр storage/потребителей; определить
   какие legacy local данные единственные, не удалять их без безопасного переноса.
2. Внести через SCHEMA-REQUESTS необходимые server contracts/политики. Сначала
   ownership и авторитетные транзакции, потом переключение UI.
3. Исправить общий error/ack контракт `cabinetApi` и вызвать его с await во всех
   потребителях. Каждый вертикальный срез проверять до следующего.
4. Перевести portal/content/series/waitlist; затем notifications/payment/calendar
   side effects. Не принимать local fallback за временное production-решение.
5. Удалить общие browser keys и рабочие demo ветки после проверенной миграции;
   сохранить private vault, не импортировать demo payments/bookings в production.
6. Обновить тесты и документацию, независимый Challenger, controlled merge,
   Main Re-Audit нового SHA, production acceptance, только затем завершение.

Rollback не должен восстанавливать local-success или стирать личные данные.
Если server slice недоступен, отключить соответствующее действие с понятной
ошибкой; не менять непересекающийся функционал.

## 9. ОСТАВШИЕСЯ РИСКИ / STOP THE LINE

P1: ложный успех сохранения, уведомления, согласия, денег и общих операций.
Остановка касается **приёмки/расширения/rollout этих дефектных сценариев**;
диагностика и исправление разрешены. Сайт в production здесь не отключался.
Containment в runtime ещё не выполнен; предложено блокировать неподтверждаемые
действия вместо демонстрационного успеха. Остаточный риск сохраняется.
Ответственный за координацию — сопровождающий @A1Dmitry; исполнитель реализации
должен взять отдельный claim, не предполагается назначенным автоматически.
Следующая проверка — перед началом каждого связанного изменения/rollout.
Возобновление: исправление + негативные/E2E + независимый Challenger + Main
Re-Audit + решение сопровождающего. Одно создание issue не снимает Stop the Line.
