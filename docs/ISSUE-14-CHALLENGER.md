## 2. РЕЗУЛЬТАТ

**Найден и исправлен один дефект (P2): пароль сейфа с формы регистрации
терялся.** Форма регистрации помечала поле «Пароль кабинета \*» обязательным
(`index.html`), `AuthViewModel` собирал его в `this.password` — и дальше значение
нигде не использовалось: `verifyCode` его не принимал, сейф клиентов оставался
незадатым, пользователь был уверен в обратном. Попутно вскрыто системное
расхождение: комментарий UI обещал «key_verifier → сервер», но
`supabaseSync.pushProfile` вырезал `key_verifier` перед отправкой — verifier
никогда не покидал устройство, хотя колонка `psychologists.key_verifier` в схеме
есть и `psyMapper` её читает.

Исправление (каноническое, Poka-Yoke):

- `js/services/cryptoService.js` — ЕДИНСТВЕННОЕ правило пароля сейфа:
  `MIN_VAULT_PASSWORD_LENGTH` + `vaultPasswordError()` (пусто = опция,
  задан = минимум 6 символов). Ранее минимум «6» дублировался в
  `initVaultPassword`, `minlength` формы и подразумевался в сообщениях.
- `js/services/authService.js` — `verifyCode(email, code, profile, vaultPassword)`:
  валидация пароля ДО обращения к серверу (одноразовый код не тратится);
  после успешного входа пароль применяется: новый кабинет → `initVaultPassword`,
  существующий (claim) → `unlockVault` — пароль с формы не может подменить
  чужой verifier. `initVaultPassword` сам отправляет verifier на сервер.
- `js/services/supabaseSync.js` — новый `pushKeyVerifier()`: PATCH только
  `key_verifier` в контексте владельца. Единственный легитимный писатель;
  `pushProfile` по-прежнему verifier не трогает (защита от записи из
  публичного контекста — прежний инвариант сохранён).
- `js/viewmodels/AuthViewModel.js` — `confirmCode()` передаёт `this.password`.
- `index.html` — подписка поля приведена к факту: «необязательно, минимум
  6 символов» + честная справка (можно задать позже во вкладке «Клиенты»).

Остальные пункты чек-листа Challenger (см. раздел 4): расхождений «код ↔ схема ↔
Edge Function ↔ документация» по auth-контуру больше не найдено.

## 7. КОРЕННЫЕ ПРИЧИНЫ (5 Почему)

Симптом: пароль собирался, но терялся. Почему: `AuthViewModel.confirmCode`
вызывал `verifyCode(email, code, profile)` — пароль в контракт не входил.
Почему контракт без пароля: канонизация registration (#7/#11) определила
контракт по полям профиля, пароль сейфа остался «полем UI». Почему это
прошло проверки: тесты проверяли use case `registration.js`, а склейку
«форма → authService → сейф» не проверял никто (слепая зона между доменом
и сервисом). Почему зона была слепой: тестовый план строился от DoD #11,
где сейф упомянут только как «семантика отдельно от Auth» — не как контракт.
Системная причина: контракт слоя сервиса (`authService`) не был покрыт
контрактным тестом — проверялся только домен.

## 8. РЕМОНТ (Poka-Yoke)

- Контракт `verifyCode` теперь включает `vaultPassword`, и тест исполняет
  именно склейку «форма → сервис → сейф → сервер» (блок 8) — слепая зона
  закрыта тестом, ошибка «поле собирается, но не используется» отлавливается
  автоматически.
- Правило пароля — одна функция (`vaultPasswordError`); повторить «6» в
  третьем месте больше нельзя без расходждения с каноном.
- `pushKeyVerifier` — единственная дверь для `key_verifier` на сервер;
  `pushProfile` физически не может его перезаписать.
- Kaizen: следующий существенный fix обязан включать контрактный тест на
  склейку сервисного слоя (не только на доменную функцию) — форма дополнена
  в `docs/RULES.md` §6.4 ранее, здесь правило применено.
